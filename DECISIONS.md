# Decisions & Trade-offs

A record of what was chosen, what was rejected, and why — the questions a judge would ask.

| Decision | Alternative considered | Why this was chosen |
|---|---|---|
| Deterministic rules engine for "meaningful change" | An ML/scoring model | Groww's own brand principles emphasize transparency and trust with users' money. A rules engine can always answer "why was I shown this?" in plain language (`reasons[]`). A trained model would need validation, drift monitoring, and still couldn't be explained as precisely in a 72-hour build. Explainability was worth more than sophistication here. |
| No buy/sell recommendations or price predictions | Adding an "AI insight" or suggested action | The brief asks the system to surface *change*, not to *advise*. Predictions carry a much higher trust and correctness burden than the problem actually requires, and Groww's "Responsible" principle argues against implying financial advice from an unvalidated system. |
| Two-signal threshold for "high" attention, one signal for "notable" | A single flat percentage threshold (e.g. "any move >2%") | A flat threshold is what the brief explicitly warns against ("don't build the obvious watchlist"). Requiring corroborating signals (price + volume, or price + market-divergence) reduces false positives from ordinary daily noise. |
| Unusualness computed against the stock's *own* 30-day average move | A single global "unusual" threshold for all stocks | A 3% move is routine for a volatile stock and unusual for a stable one. Comparing each stock to its own history is more honest about what "unusual" means, at the cost of one extra `yfinance` history call per Asset Detail view. |
| `yfinance` for market data | A paid market data API (e.g. Alpha Vantage, Twelve Data) | Free, no API key, no rate-limit friction under hackathon time pressure, and provides price, volume, and news in one library. Trade-off: not a real-time institutional feed — acceptable for this scope, and disclosed via `data_quality` badges rather than hidden. |
| Single demo user (`demo_user`), no authentication | Building login/signup | Every data model is already keyed by `user_id`, so adding real auth later is additive, not a redesign. Building auth in the final hours would have meant touching every existing endpoint under time pressure, risking a broken submission for a feature the brief didn't require. |
| Manual "Simulate Data Outage" toggle | Just writing about resilience in the README | The brief explicitly asks "how do you handle stale, delayed, or conflicting data?" — a judge can click the toggle and watch the fallback happen in real time instead of taking a written claim on faith. |
| Cache-and-fallback (last-known-good) instead of retry/backoff | Retrying the failed request with exponential backoff | A user checking a watchlist wants an answer *now*, even if slightly stale, rather than a spinner. Retrying adds latency without guaranteeing success; falling back to the last good value keeps the UI responsive and is honestly labeled as stale. |
| Symbol alias/resolution table (`resolve_symbol`) | Requiring users to type exact Yahoo Finance tickers | Real users type "Infosys," not "INFY.NS." Real tickers also change (Zomato → Eternal) independent of anything the user does. Handling this in one place keeps every downstream consumer (quote, context, asset-detail) correct without duplicating logic. |
| Parallelized attention fetches (`Promise.all`) on the frontend | Sequential fetch loop (the original implementation) | With a sequential loop, a 10-stock watchlist takes roughly 10× as long to load as a single stock. This is a direct scalability answer for larger watchlists, changed after profiling the original loop felt slow. |
| Single-file `App.jsx` rather than a deep component tree | Splitting into many small component files/folders | Given the 72-hour window, a flat, readable file was faster to build and review correctly than maintaining prop-drilling across a deeper folder structure. This is a conscious "keep it simple" choice, not an oversight — acknowledged directly rather than disguised. |
| Deployed on Render (backend) + Vercel (frontend) + MongoDB Atlas | A single all-in-one host | Free tiers on all three, and separating frontend/backend deploys matches how the codebase is actually split, making the CORS boundary explicit and testable rather than implicit. |
